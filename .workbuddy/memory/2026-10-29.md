# 2026-10-29

## 完善项目：查找替换、最近文件、崩溃恢复草稿

起点：219 测试全绿，无 TODO。审计后找到三处"承诺/数据存在但功能缺失"的空缺。

### 1. 查找 / 替换（新增 `src/find.rs`，约 380 行含测试）

- README 一直写 `Ctrl+F` 查找，但 `shortcuts()` 里没有 `Key::F`，全项目无查找
  UI。这是文档与实现不一致，属于必须修的缺陷，不是新功能。
- `find.rs` 只做匹配与光标推进：`find_all` 返回**字节区间**，因为块的 span、
  `Document::replace_span` 都是字节；`replace_all` 一次拼装新字符串，避免
  N 次 reparse 且避免"改完一处后面偏移全失效"。
- 大小写折叠**只做 ASCII**：Unicode 折叠会改变字节长度（`İ` → 两个字符），
  每个后续偏移都会错位，替换时会切坏 UTF-8。中文无大小写，不受影响。
- 命中定位：`EditorAction::Focus` 的 `caret` 参数一直是忽略的，所以新增
  `ViewState::pending_selection`（**字符**索引，块内偏移），在
  `edit::take_focus()` 里于 widget 建好后写入 `TextEditState.cursor`。
  字节↔字符转换统一走 `edit::char_to_byte` / 新增的 `edit::byte_to_char`。
- 只绘制、没有 TextEdit 的块（`Rule`、`Html`）要**跳过**，否则 `focus_requested`
  会一直挂着，等下一个可编辑块出现时抢焦点。源码模式另有路径：
  `App::source_selection` 在 `source_pane` 里装进 `mdp-source` 那个 TextEdit。
- 「全部替换」一次性 `replace_span(0..len, new)`，所以是**一步撤销**，
  有测试用"一次 undo 是否复原"来锁这个性质。

### 2. 最近文件菜单

`config.recent` 之前只被 `push_recent` / `prune_recent` 维护，**没有任何 UI
能打开它**。「打开」改成菜单：文件对话框 + 最近 12 条。磁盘上已消失的条目
直接摘掉并提示，不弹模态框。

### 3. 崩溃恢复草稿（新增 `src/recovery.rs`）

- 脏文档每 3 秒镜像到 `%APPDATA%\MarkdownPad\draft.json`（写临时文件再 rename）。
- **草稿从不自动应用**，只在状态栏给「恢复草稿」「丢弃」两个按钮。理由与
  滚动偏移那次事故同源：跨启动恢复"不可验证的持久状态"会出事，能恢复的东西
  必须是用户看得见、也能拒绝的。
- 节流跳过时必须 `ctx.request_repaint_after(剩余时间)`，否则最后几秒输入
  永远等不到下一帧——空闲窗口不产生帧，这段窗口恰好是崩溃最可能落进去的。
- 测试隔离：`Draft::path_on_disk()` 在 `cfg!(test)` 且无覆盖时返回 `None`，
  测试用 `DraftAtTemp`（RAII）临时改道，绝不碰用户的真实 draft.json。
  注意顺序：**先改道再 discard**，否则会删掉开发者自己的草稿。

## 第二轮：提醒框改为官方图标与真实结构

用户反馈「这些提示框不要用自己搞的东西，否则即见即所得就没优势，看起来非常怪异」。
排查后是**两个问题叠在一起**，第二个比第一个严重。

### 1. 解析缺陷：连续提醒框只识别第一个（根因）

`parse_quote` 里有一条「空行 + 下一行仍是 `>` 就当作同一引用的续行」的分支
（`doc/block.rs`）。于是 `> [!NOTE] … 空行 … > [!TIP]` 被合并成**一个块**：
第一个提醒框吞掉后面全部内容，`[!TIP]` / `[!WARNING]` 以原文形式变成它的正文。
CommonMark 里空行即结束引用，跨段继续必须在空行上写 `>`（那走的是另一分支）。
删掉该分支即可，已加回归测试 `consecutive_alerts_stay_separate_blocks` 与
`a_quote_can_still_span_a_paragraph_break_with_a_marker`。

**教训：用户说「看起来怪异」时，先查内容有没有正确解析，再查样式。**

### 2. 样式：图标是手挑的 Unicode 字符

原来 `icon_for` 返回 `✎ ℹ ✔ ★ ⚠ ✖ ☠ ☰ ❝`，字重、光学大小、基线全由字体决定，
和正文混排必然不齐，也不是目标站点的图标。

现在 `assets/icons/` 存官方原始文件（octicons MIT / lucide ISC / Docusaurus MIT），
`tools/extract_icons.py` 生成 `src/icon_data.rs`（`d` 属性逐字节复制），
`src/icon.rs` 负责解析与几何化：

- SVG 路径子集 `M L H V C S Q T A Z`，含紧凑弧线标志位写法 `a1 1 0 011 1`
- 曲线展开容差按 viewBox 比例算，16px 与 40px 都圆
- **扫描线梯形填充**，支持非零环绕与奇偶两种规则：octicons 靠反向缠绕挖孔
  （`info` 的环），Docusaurus 显式 `fill-rule="evenodd"`。egui 只有凸多边形，
  凹形（`zap` 闪电、`report` 气泡）必须自己三角化。
- 退化描边（lucide 的 `h.01` 圆点）要转成 dot，egui 的 butt-cap 画不出来。

结构与配色按各自 CSS：GitHub 4px 左竖线 + 无底色 + 词首大写（原来错写成大写）；
Obsidian 1px 描边 + 10% 底色、无竖线；VitePress 只有柔和底色（默认 border 是
transparent）；Docusaurus 竖线 + 1.6em 图标 + 全大写标题。GitHub 用 primer 色值，
Obsidian 用 `--color-*-rgb`。**底色要按 `palette.paper` 混合，不是 `canvas`**——
后者是桌面色，会让「无底色」的 GitHub 在纸上画出一块略深的矩形。

### 视觉复核的办法（可复用）

本机 PowerShell 的 `Add-Type` 被安全策略禁止，截不了屏。两条可行路径：

1. **几何导出 + 自栅格化**：`cargo test dump_icon_geometry -- --ignored` 把每个
   图标的三角形/折线/圆写到 `%TEMP%\mdpad-icons.txt`，再用纯 Python（zlib 手写
   PNG）栅格化，能看清环孔、感叹号内切、圆点是否都在。
2. **egui 自抓帧**：`ctx.request_screenshot(move |img| …)` 是 0.37 的正确入口
   （没有 `Event::Screenshot`，也没有 `UserData`）。抓到的 `ColorImage` 手写成
   24 位 BMP 即可，`ViewImage` 能读。空闲窗口不出帧，取证期间必须
   `request_repaint()`，否则帧号永远到不了。

临时取证代码用完已回退，不留在产品里。

## 内存基线实测（16:0x）

用户质疑「316MB 太肥」。实测（release，Intel Arc 核显）：

| 场景 | 私有提交 |
|---|---|
| 最小 eframe 空窗口（Hello World） | 318.8 MB |
| 本编辑器，空文档 | 365.2 MB |
| 3000 块纯文本 | 399.0 MB |
| 9000 块纯文本 | 449.0 MB |
| 9000 块含公式/行内代码 | 470.6 MB |

结论：**图形栈地板就是 319MB**，不是我们的代码。进程 101 个模块共 365MB，
自身 exe 只 18MB，其余是 Intel 驱动（igc64 81MB、igd12um64xeh 57MB、igvk64 23MB）
以及被一并载入的 d3d10warp/dxgi。自研部分两笔：字体文件常驻 46MB
（msyh 19.7 + msyhbd 16.9 + 其余），内容 ~9.3KB/块（含公式/代码 +2.4KB/块）。

对照实验手法：项目内加 `examples/memprobe.rs`（20 行 eframe 空窗口），
`cargo build --release --example memprobe` 后分别启动、用
`Get-Process | WorkingSet64/PrivateMemorySize64` 读，跑完即删。这个方法比猜有效得多。

**可优化但未做**：整篇排版→视口内排版（内容内存从 O(块数) 降到 O(视口)）。
改动面涉及滚动、命中测试、查找跳转，属结构性改造，等用户点头。

## 渲染后端按平台可选（15:5x）

用户要求：默认跟随平台，设置里可改；不兼容的选项必须置灰。
实现：`config::Backend`（Auto/DirectX/Vulkan/Metal/OpenGl），
`platform_order()` 决定默认与兜底顺序，`effective()` 降级，`unavailable_reason()` 给置灰理由。

**实测（同机 Intel Arc，1320x900 空文档，专用工作集）**：
- wgpu 默认全后端：365MB 私有提交 / 101 模块
- DX12 单后端：**342MB**
- OpenGL(glow)：**102.6MB** ← 因此 Windows 默认改为 OpenGL

关键发现：eframe 0.37 的默认 feature 是 **wgpu**（不是 glow）。不指定 backends 时
wgpu 会枚 DX12+Vulkan+WARP，把 Intel 的 igc64(81MB)/igvk64(23MB) 一起拉进来 ——
这就是「316MB」的来源。`WgpuSetupCreateNew::instance_descriptor.backends` 可收窄。

启用 `glow` feature 会改变 `App::on_exit` 的签名（多一个 `Option<&glow::Context>`）。

失效兜底：事件循环一个进程只能建一次，所以不能当场重试；失败时把 `backend.fallback()`
写回配置，下次启动用下一个候选。

## 字体改为映射（16:0x）

`FontData::from_blob` 接受 `Arc<dyn AsRef<[u8]>>`，用 `memmap2::Mmap` 传进去即可，
不必 `fs::read` 把整个字体文件搬进堆（epaint 的类型别名注释里就写了这个用法）。
`Mmap` 实现了 `AsRef<[u8]>`；map 失败时退回 `fs::read`，类型同一个。

同机同一空文档（OpenGL，专用工作集，启动后 6 秒采样）：
- 堆上字体：103 MB
- 映射字体：**72 MB**（瞬时），20 秒后稳定 **45–48 MB**

决定性对照：临时加 `MDPAD_NOFONT` 跳过系统字体 → 36.0MB，与 GL 空窗口基线 35.7MB 一致，
说明我们自己的代码几乎不额外占内存，剩下全是字体页。字体页即使映射也会被 ab_glyph
解析时触碰而计入工作集，所以**再压只能少装字体**；而系统的中文字面没有明显更小的
（雅黑 19.7/16.9、等线 16.3/16.5、宋体 18.3），换字体的收益不值产品观感。

`[profile.release] lto` 实测只差 0.3MB 却让构建从 12s 变 85s，已弃用；只保留 `strip = true`。

**采样方法要注意**：启动后立刻读会偏高（字体页刚被触碰），Windows 空闲一段时间会 trim，
要隔十几秒多次采样才有稳定值。
